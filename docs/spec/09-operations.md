# 09 — Operations

## 1. Configuration

All configuration comes from environment variables (Node) or vars/secrets (Cloudflare), parsed and
validated by one Zod schema at startup. Invalid config → refuse to start with a clear message that
names the variable and the rule but **never includes a secret's value** (secret fields are redacted
in every startup and config error, including Zod's received-value text and the `_FILE` equality
check). `.env.example` documents every variable. On Node every secret may instead be given as a
file: `<NAME>_FILE=/run/secrets/<name>` (Docker secrets) is read at startup and wins over `<NAME>`,
so secrets don't show up in `docker inspect` or the process environment; exactly one trailing
newline (`\n` or `\r\n`) is trimmed from the file's contents; setting both is allowed only if they're
equal.

### 1.1 Secret derivation and rotation

Subkeys are derived from `APP_SECRET` with HKDF-SHA256 (empty salt, 32-byte output used as an
HMAC-SHA256 key), each with a distinct, versioned `info` label:

| Label | Used for | Effect of changing it |
|---|---|---|
| `otp/v1` | OTP code hashing | live codes stop working (≤ 10 min impact) |
| `ip/v1` | IP-bucket hashing in rate limits and audit events | rate-limit counters reset; audit correlation breaks |
| `unsub/v1` | unsubscribe token MAC | old unsubscribe links stop working — **avoid**; if rotated, keep verifying `v1` too |
| `email-id/v1` | `emailId` = HMAC of normalised email: suppression list, per-target invite limits, `users.email_id` (nudge unsubscribe), log identifiers | **suppression list silently empties** → previously unsubscribed/bounced addresses get mailed again, and nudge unsubscribe links stop finding their account. Never rotate this subkey without re-keying the tables. |
| `token/v1` | API token hashing (06 §8) | every API token stops working — users must create new ones |

Rotation procedure (documented in `docs/deploy.md`): introduce `APP_SECRET_PREVIOUS`; derive `v1`
keys from the previous secret for verification of `unsub` and for `email-id` lookups while a
one-off job re-hashes `email_suppressions` and `users.email_id` (and new `v2` labels are used for
writes). That job must keep every `nudges` unsubscribe link already sent resolvable: the tokens
don't expire and carry the `v1` `emailId`, so while it runs and afterwards the unsubscribe route
also looks accounts up by the `v1` `emailId` of each nudged user's stored `users.email` (or keeps a
`v1` column beside the new one) — a valid old link must still turn nudges off. Its page stays the
same whether or not it found an account (no oracle), so the requirement is the lookup, not the
answer. Until that job exists, **rotating `APP_SECRET` is unsupported** and the docs say so.

### 1.2 Admin commands

Every administrative task is an Admin API endpoint (05 §Admin API) — Workers has no shell. The
`pnpm admin:*` scripts are thin clients of that API: they read `ADMIN_URL` (the instance's
`PUBLIC_URL`) and an `admin` token (exclusive scope, ≤ 30 days, 06 §8) from `ADMIN_TOKEN_FILE`
(preferred: a 0600 file) or `ADMIN_TOKEN` in the operator's shell, never from the repository. The
Admin API and these commands arrive with API tokens in M3 (10); before that, M2 has no admin
surface beyond config. Commands: `admin:status`, `admin:user:lookup`,
`admin:user:suspend`, `admin:user:unsuspend`, `admin:user:delete`, `admin:game:cancel`,
`admin:dict:add`, `admin:dict:delete`, `admin:suppression:remove`, `admin:audit`.

### 1.3 Installing games

The installed games are listed in `instance.config.ts` (02 §7.3). To add a third-party game:
add the package to the root `package.json` **`dependencies`** from a registry you name explicitly
in `.npmrc`, add it to `instance.config.ts`, run `pnpm build` (which runs `pnpm games:verify`
in fast mode; CI runs the full kit), and deploy. To **remove** a game type or upgrade to a package
major that drops a rules version, first let its live games finish or cancel them (Admin API): the
deploy job's `pnpm games:check-db` (Cloudflare) and the Node server's startup check refuse to go
ahead while `lobby`/`active` games would be orphaned, unless you pass `--allow-orphans` to the
deploy step or start Node with `ALLOW_ORPHAN_GAMES` set to the digest its refusal printed (02 §7.3). **Also remove the
removed game's `GAMES_<TYPE>_*` variables**: left behind, they block startup (§1).

Before installing, read 02 §7.5: **a game package is fully trusted** — it runs inside your server
and in your players' browsers with their sessions, and a malicious one can take over the instance
and players' accounts. Install games only from authors you trust, pin the version, read the diff
on every upgrade (Renovate never merges anything by itself, 11 §8), and **don't play games on an
admin account**.

## 2. Email delivery

Email is critical (no email = no sign-in). The `EmailSender` interface has HTTP-API implementations
that work on both runtimes, plus SMTP for Node only.

- **Proof of concept (Q2): the `gmail` provider, on both runtimes**, sending from a dedicated user
  in the owner's Google Workspace domain.
  - It calls the Gmail API `users.messages.send` with an access token obtained from
    `GMAIL_REFRESH_TOKEN` (cached until shortly before expiry). **No domain-wide delegation and no
    app password**: delegation can't be limited to one user, and an app password also opens the
    whole mailbox over IMAP/POP. A leaked refresh token can only send mail as the sender user
    (08 T15).
  - Messages are raw MIME built by the shared MIME builder (RFC 2047 encoding, CR/LF rejected in
    every header, 08 T14). The builder converts nothing in an address: a recipient that isn't
    already an ASCII `addr-spec` is refused, because the stored address (04 conventions) must be
    the one delivered to. Requests to Google never follow a redirect (`redirect: "manual"`, which
    both runtimes support; any `3xx` is a failure).
  - Gmail keeps a copy of every sent message in the sender's *Sent* folder; that is an accepted
    proof-of-concept residual with mitigations (08 §5).
  - Gmail's per-user sending limit is 2,000 messages in any 24 hours for a paid Workspace user
    (500 on a trial), and Google may change it. The instance-wide email caps send at most 1,500 in
    any 24 hours with their defaults, and startup refuses caps that could exceed
    `EMAIL_DAILY_QUOTA` (08 §4.2, §1). Use the sender user for one instance only: two instances
    sharing it share its quota.
  - Move to a dedicated transactional provider before the instance grows beyond friends and family.
- **Operator setup for `gmail`** (done once by the owner, in their Google accounts; documented in
  `docs/deploy.md`):
  1. Create a dedicated Workspace user for sending (e.g. `no-reply@…`), used for nothing else and
     never used interactively after setup; turn on 2-Step Verification for it; disable IMAP and POP
     for it; set up a regular purge of its *Sent* folder (or a retention rule if the edition
     supports one). Purged messages stay in Trash for 30 days, and any Vault hold keeps them longer;
     the privacy page's retention statement must allow for both (08 §5).
  2. In a Google Cloud project, enable the Gmail API, set the consent screen's user type to
     **Internal** with the single scope `gmail.send`, and create an OAuth client of type **Desktop
     app** (the only type that accepts a loopback redirect on a random port).
  3. Sign in as the sender user once with the `pnpm gmail:authorize` helper to obtain the refresh
     token. The helper:
     - runs the OAuth authorization-code flow with **PKCE** and a random `state`, on a loopback
       redirect bound to `127.0.0.1` (a random port), with `login_hint=GMAIL_SENDER`;
     - requests exactly `openid email https://www.googleapis.com/auth/gmail.send`, never
       `include_granted_scopes`;
     - refuses the result unless the `id_token`'s verified `email` equals `GMAIL_SENDER` and the
       granted scope set is exactly the requested one (so authorising while signed in as the
       wrong account, e.g. an admin, fails instead of sending from their mailbox);
     - reads the client id and secret from the environment or a file (`GMAIL_CLIENT_ID_FILE`,
       `GMAIL_CLIENT_SECRET_FILE`), never from argv;
     - writes the refresh token to a new file with mode `0600` outside the repository, and never
       prints it; on any refusal it revokes the token it was just given and writes nothing.

     The server re-checks the token on **every refresh** (so on Workers too, which have no startup
     step), and the check **fails closed**: the granted scope set must be exactly `openid`, `email`
     and `gmail.send`, and the response must carry a parseable `id_token` for this client (`aud` is
     the client id) whose `email` is `GMAIL_SENDER` and `email_verified` is true. Anything else
     (another scope, a missing or unparseable `id_token`, another audience, an unverified or
     different address) refuses to send and logs an error-level alert (`email_token_scope`,
     `email_token_account`), which names only the known scope names and a count of the others. On
     Node it also refreshes once at startup and, for those two refusals, refuses to start; Google being unreachable or having revoked the
     token does not stop the server starting (it logs `email_token_failed` or
     `email_credentials_rejected`, and then the same on every message).
  4. Store `GMAIL_CLIENT_ID`, `GMAIL_CLIENT_SECRET`, `GMAIL_REFRESH_TOKEN` and `GMAIL_SENDER` as
     Worker secrets or Docker secrets (`*_FILE`). To revoke, remove the app's access from the sender
     user's Google account and repeat step 3.
- The generic `smtp` provider (Node only) stays available for operators with their own SMTP relay.
- **Failures and alerts.** A message that can't be sent rejects, and the background task that
  sent it logs nothing more: the sender has already logged one error-level entry with a fixed
  `alert` (`email_send_failed` with the HTTP `status` where there is one, `email_token_failed`,
  `email_credentials_rejected`) and the provider, never an address, a message, a token or
  Google's response text, and the background task that called it is told the failure was already
  alerted (it logs no "background task failed" on top). A `401` from Gmail refreshes the token once and retries once; nothing
  else is retried (the person asks for a new code, 06 §3).
- **Providers not built yet.** Until a provider's implementation lands (`smtp` once
  Q26 is decided, 10 M2; `resend`, `postmark`, `ses` and `cloudflare` when scheduled), a configuration naming it still
  starts, logs an error-level `email_provider_unavailable` alert at startup and on every message, and sends
  nothing; the API keeps its normal responses. Only `console` (local-dev) sends in M2.
- Also supported: a transactional provider with an HTTP API (Resend, Postmark, Amazon SES).
  Cloudflare's own Email Service is supported via its `send_email` binding *if* it's available on
  the operator's account (Email Routing's older `send_email` binding only sends to verified
  addresses and is NOT suitable).
- The sending domain MUST have SPF, DKIM and DMARC configured (for the Workspace domain these should
  already exist — verify before go-live); document this in `docs/deploy.md`.
- Every non-OTP email carries `List-Unsubscribe` (pointing at `/api/v1/email/unsubscribe`, 05) and
  `List-Unsubscribe-Post: List-Unsubscribe=One-Click` headers; the `gmail` (raw MIME) and `smtp`
  paths support them.
- Templates: plain-text + minimal HTML, no remote images, no tracking pixels, no link tracking.
- Bounce/complaint webhooks (provider-specific) feed `email_suppressions` — nice-to-have in v1.
- Dev: `console` provider plus a `/__dev/emails` page listing captured emails so Playwright can read
  OTPs. Both are available only when `isLocalDev(config)` is true (06 §4) — a runtime check, not
  just a build flag — and the CI suite asserts `/__dev/emails` is 404 in a production-config build.

## 3. Cloudflare deployment

- Worker with: Static Assets (built SPA), D1 binding `DB`, Durable Object binding `USER_CHANNEL`
  (SQLite-backed DO class, declared in migrations), Cron Trigger `*/15 * * * *`.
- The Cron Trigger runs the sweep (03 §8). One invocation has a bounded budget of D1 queries and
  subrequests, so a Worker run expires at most 1 overdue lobby, claims at most 1 email-invite seat,
  deletes at most 100 expired join links and sends at most 2 email nudges (Node: 100 of each, and
  1,000 join links); the rest wait 15 minutes for the next one
  (alpha A17 halved the nudges from A6's 4 to make room). The arithmetic, counting every
  statement of a batch as a query (the conservative reading): the lobby step's list (1), and per
  lobby its load (2) and the expiry transition (1, plus one per row with a typed address: 1 for a
  two-seat game) — 5; the claim step's list (1), and per seat the game's load (2), the block
  lookup (1) and the claim (1) — 5; the nudge step's instance-wide cap read (2 statements), due list
  (1) and, when capped, the once-per-window alert counter (2) — at most 5, the join-link step's one
  delete (1, alpha A18), and per nudge the
  recipient's cap read (2), the claim (1), counting both caps (4), the game's players (1), their
  users (1) and the last move (1) — 10. So a run is at most 5 + 5 + 1 + 25 = 36 statements for
  two-seat games (42 with a full eight-seat lobby); a claimed `normal` invitation's push (alpha
  A20) adds the subscriptions (1) and, for a claimant with a device, the daily counter (2), the
  delivery marks (1) and the deletions (1) — 41 (47), inside the Workers Free plan's per-invocation
  D1 query limit (50 at the time of writing; check the current Cloudflare limits). A lost race
  retries a lobby's expiry or a claim from its load, at most three more times (03 §5.2), which
  can add up to 24 in the worst case; that needs a concurrent request on the same lobby in that moment,
  and a run that goes over fails and is picked up by the next. **Workers residual (review
  A17-S-6):** expiring one overdue lobby per run (96 a day) can fall behind if more lobbies than
  that fall due in a day; lazy expiry (03 §8) still expires each one the moment anyone involved
  comes back, and nothing accepts or starts an overdue lobby, so the backlog only delays clearing
  typed addresses (F-16's residual); re-measure at the first Workers deployment (10).
- **Requests that do several statements per address (alpha A17 review S-5).** Counted the same
  conservative way (every statement of a batch, the session's refresh included):
  - `POST /api/v1/games` with `n` typed addresses: 25 statements plus 17 per address (the caps,
    the lookups, the per-pair counts, the inbound cap's one read of live invitations, alpha A20
    review S-1, the two tiers of invite-email caps, and the seat and `invites` row in the insert).
    One address (every two-seat game, so every words game) is 42–45 in the request, inside the
    Free plan's 50; two or more addresses are over it (59 for two, up to 144 for seven), and so is
    any create that lazily expires the creator's overdue lobbies (up to 20 of them, 03 §8). Its
    background task runs in the same invocation, in this order (review A20-S-2, P-1): 2 for the
    instance cap's alert and day stop when the cap stopped an email, then the sends, then 1 to
    record `sent_at`, and only then the invitation push (alpha A20, when a `normal` invitation with
    a user was seated and push is configured): the read of the game (2), the subscriptions (1),
    and for invitees with a device the daily counter (2 each), the delivery marks (1) and the
    deletions (1). One known invitee with a device is therefore 42 + 1 (`sent_at`) + 7 (the push)
    = 50 statements, or 52 with the alert's 2 when the instance cap stopped an email: **at or over
    the Free plan's 50**. Because the push comes last, the F-20 stop and `sent_at` have landed by
    about statement 48, inside the limit, and a statement over it is one of the push's
    (review A20-P2-1). A
    pick seated as an invitation adds the two shared invite-email counters (4), and a request with
    such a pick but no typed address the suppression and past-opponent reads and the instance
    cap's stop marker (4). Those **need the Paid plan, or the invitation push in an invocation of
    its own** (10, First Workers deployment).
  - The `PATCH /api/v1/me` that completes onboarding: 4 statements plus 4 per claimed seat (the

    deletions are not a normal-case cost.
    Node claims up to 50 per request. Each nudge also makes one provider subrequest (the `gmail` provider

  as failed (not retried), so it shows in the trigger's history. Re-measure the per-invocation
  cost at the first Workers deployment (10).
- Web Push (alpha A8) runs in the `waitUntil` of the request whose transition it reports: one
  subrequest per subscription, at most 40 per transition (inside the Free plan's 50 subrequests
  per invocation), and four D1 statements however many devices (the subscriptions, the names,
  the delivery marks and the deletions). Re-measure with the rest at the first Workers
  deployment.
- `apps/worker/wrangler.example.toml` is committed with no account-specific IDs; operators copy it to

- The example sets `workers_dev = false` and `preview_urls = false` (with a comment: enable

  origins.
- Smart Placement enabled (03 §11).
- R2 bucket binding `BLOBS` for `BlobStore` (uploaded/operator dictionaries). Private bucket, no

## 4. Docker deployment

- Multi-stage `apps/node/Dockerfile`: build with pnpm, runtime on a slim Node LTS image pinned by
  digest; runs as non-root UID; read-only root filesystem except `/data`; `EXPOSE 8080`;
  `HEALTHCHECK` on `/api/health` (which needs no `CF-Connecting-IP`, 08 §4.1). The server starts
  with `node --disallow-code-generation-from-strings` and then, in order (02 §7.3): reads and
  validates config and secrets (`*_FILE`); takes the single-instance lock; applies migrations (04
  §Migrations); checks for orphaned games using only `generated/installed.json`; scrubs secrets
  from `process.env`; loads the generated game registry with a dynamic `import()` (02 §7.5) and refuses to start if it doesn't match
  `installed.json`; then serves.
- Deployments pull the image **by digest** (`image: registry…/your-move@sha256:…`), taken from the
  release notes (from M1; until then from the `publish:image` job's output); tags are for humans
  only (images aren't signed yet, 08 §6).
- Two compose examples in `apps/node/` (the only names used anywhere), both with named volumes for
  `/data` and (separately) `/data/blobs`, and app secrets supplied as Docker secrets (`*_FILE`, §1):
  - `docker-compose.tunnel.yml` (**the proof-of-concept deployment**, Q6; an M4 deliverable):
    app + `cloudflared` (Cloudflare Tunnel, token from a Docker secret) publishing the app on a
    hostname in the owner's Cloudflare-managed domain. No host ports are published and no inbound
    firewall rules are needed; TLS terminates at Cloudflare. `TRUST_PROXY=cloudflare`,
    `PUBLIC_URL=https://<hostname>`. The tunnel's public hostname must route only to the app
    container (no catch-all rule). In the Cloudflare dashboard, **Pseudo IPv4** must be off or
    "Add header", never "Overwrite" (08 §4.1). Optionally, a Cloudflare Access policy can gate the
    whole site during early testing.
  - `docker-compose.caddy.yml`: app + Caddy (automatic HTTPS) as reverse proxy, `TRUST_PROXY=xff`.
- Image name and labels come from build args — no product name baked in.
- Backups: documented options — nightly `sqlite3 /data/app.sqlite ".backup ..."` sidecar, or
  Litestream to S3-compatible storage. Recommended retention 30 days (deleted accounts disappear from
  backups within that window; stated on the privacy page). Cloudflare: D1 Time Travel (30 days on
  paid plans) — same statement.
- **Networks**: the app's port is **never** published to the host. Two networks:
  - `front` (`internal: true`), shared only by the app and Caddy or `cloudflared`, so nothing else
    can reach the app's port (otherwise `X-Forwarded-For`/`CF-Connecting-IP` could be spoofed by
    connecting directly; `TRUST_PROXY_PEERS` is the second line of defence, 08 §4.1). Its subnet is
    **pinned with IPAM** in both compose files (e.g. `172.30.99.0/28`), and so is the proxy's
    address on it. The Docker host has an address on `front` too (the bridge gateway), so the
    compose files set `TRUST_PROXY_PEERS` to exactly **the proxy's pinned address**
    (the container's own health check needs no client address, so loopback is not trusted), never the whole subnet. The tunnel
    reaches the app through a front-only alias (`app-front`): Docker resolves the service name to
    every network the app is on, including `egress`, a peer outside `TRUST_PROXY_PEERS`, so a route to the service name would be
    refused. The private-ranges default of `TRUST_PROXY_PEERS` is only a fallback for
    deployments that don't set it, and startup logs a warning when the default is in use;
  - `egress`, a normal bridge network the app needs for outbound calls (Gmail API, Web Push) and
    `cloudflared` for its tunnel connection. The app publishes nothing on it. In the Caddy compose,
    Caddy publishes 80/443 on `egress` and reaches the app over `front`; nothing publishes the
    app's port.
- Single instance only (see 03 §5.3).

## 5. Observability

- Structured JSON logs (`level`, `msg`, `requestId`, `route`, `status`, `durationMs`, `userId`
  where relevant). A request that gets an error response adds `code`, the error code the body
  carries, to its one `request` line; it is noted where the body is built and never read back from
  the response. A `400 BAD_REQUEST` that several places can raise also carries a fixed `reason`
  (`invalid_email`, `no_email` or `no_client_ip`). A request-validation failure adds `issues`: flat
  `target.path:zodCode` pairs (`json.email:too_big`), comma-separated, at most 5, with every path
  segment that isn't an identifier-shaped field name masked as `*`, and never Zod's `message`,
  `input` or `received`. `route` is the route **pattern** (`/api/v1/games/:id`), never the raw path. Never
  log OTPs, tokens, cookies, the `Authorization` header, request bodies, emails in any form other
  than the HMAC `emailId`, or game secrets. Edge logs must exclude `Authorization` too: the Caddy
  compose's log config drops it, and on Workers the operator checks that Workers Logs/Logpush don't
  record request headers (to be verified in M3, when tokens arrive). They must also leave out the
  query string of `/api/v1/email/unsubscribe` (its `t=` token turns nudges off or suppresses an
  address, and never expires, 05 §Email links): the app logs the route pattern only, Caddy's log
  config and the tunnel/edge logs drop or redact it, and on Workers the operator checks that the
  logged URL fields don't keep it.
- Validation and module errors are logged by code and path only, never with input values
  (e.g. strip Zod's `received`). Unhandled exceptions log the error class, message and stack, and
  the client gets `500 INTERNAL` with no detail (05 §Errors).
- Cloudflare: Workers Logs (retention per Cloudflare plan). Docker: stdout (operator's log
  retention). The privacy page states both.
- No third-party error tracking by default. A `/api/health` endpoint for uptime checks.

## 6. CI (GitLab)

The pipeline, its stages and the quality gates are defined in 11 §9. Deployment specifics:

- **Cloudflare deploy** arrives with the first Workers deployment (10 §First Workers
  deployment); until then the deploy stage has no job. It will be a manual job in the `production`
  environment, default branch and tags only: `pnpm games:check-db` against D1 (02 §7.3;
  `--allow-orphans` is the only override), reading only `generated/installed.json` from the
  stage-3 artifact (`games:check-db` runs as a self-contained bundle built in stage 3 and carried
  in the same artifact, since the job installs nothing), then `wrangler d1 migrations apply`, then
  `wrangler deploy --no-bundle` of `dist/worker` from the already-built artifact. wrangler comes
  from a lockfile-pinned,
  `--ignore-scripts` install carried as an artifact, its configuration is generated from CI
  variables, and the job never runs `pnpm install` or `games:verify` or imports any game package
  (credentials per 08 §6).
- **Docker images** for `linux/amd64` and `linux/arm64` are built natively on the matching shared
  runner (tags `arch-amd64`, `arch-arm64`) with kaniko (or rootless BuildKit), assembled into a multi-arch
  manifest, and — on `main` and tags only, in the `release` environment with the release registry
  token (a Maintainer-role, registry-only project access token in protected, environment-scoped
  variables; our GitLab CE has no protected environments, 08 §6) — pushed to this project's GitLab
  container registry, tagged with the version and the commit, with their SBOMs kept as pipeline
  artifacts and (from M1) their digests recorded in the release notes. MR pipelines build but
  never push, so they can't run the image (end-to-end tests run against the Node build output
  instead, 11 §9). On `main`, a **smoke job** after the push pulls the new image by digest as a CI
  `services:` container and checks that `/api/health` answers. Images aren't signed yet (08 §6).
- The owner's proof-of-concept deployment (Docker behind a Cloudflare Tunnel, Q6) pulls the image
  from the registry; a deploy job for it can follow once it exists.
