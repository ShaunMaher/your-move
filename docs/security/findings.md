# Security findings and accepted risks

Tracks security findings and knowingly accepted risks (08 §7). Ids are `F-<n>`; status is
`open`, `fixed` or `accepted-risk`. Every OSV ignore in `osv-scanner.toml` names an entry here
with the same expiry (11 §6).

| Id | Status | Source | Risk | Rationale and mitigations | Review by |
|---|---|---|---|---|---|
| F-1 | accepted-risk | 06 §3 | Per-email OTP verify lockout (temporary denial of service) | Bounds guessing; temporary; logged | M2 |
| F-2 | accepted-risk | 08 T20 | Past-opponent relationships spread through N-player auto-joins | Both-acted rule; `whoCanAddMe = nobody`; games with AI seats always invite | M4 |
| F-3 | accepted-risk | 08 T4 | Q3 residuals: signing up, then accepting or declining, reveals that an address has an account | Needs the address holder's own action | M4 |
| F-4 | accepted-risk | 08 §5, 09 §2 | Gmail *Sent*-folder copies of every email sent | Dedicated sender user, 2-Step Verification, IMAP/POP off, periodic purge (Trash keeps 30 days), disclosed on the privacy page; move to a transactional provider before the instance grows | Before growth |
| F-5 | accepted-risk | 08 T27 | Installed game packages are fully trusted: a malicious one can compromise the instance and players' accounts | Install only trusted authors; review diffs; built-output rules and globals allow-list; test kit incl. isolation; Node code generation off and secrets scrubbed before loading games; CSP; no automerge; SES/isolates later; the engine lint rules are static: they reject built-ins used other than by name, reflective and descriptor access to them, dynamic `import()`, `import.meta`, and `constructor`/`__proto__` reached through a value by name, by a static key (string or template literal without expressions) or by destructuring, but they can't follow a property name computed at run time, so they are a guardrail, not a sandbox (built-output rules and the test kit, M1, narrow this; isolation later); scrubbing `process.env` guards against accidental leaks only — the original environment stays readable from `/proc/self/environ`, so secrets are best given as `*_FILE` (docs/deploy.md) | First third-party game |
| F-6 | accepted-risk | 08 T30 | Config controls who is admin; admins who also play on their admin account | Exclusive admin tokens of ≤ 30 days, audited, every admin notified on creation; docs say not to play on admin accounts | M3 |
| F-7 | accepted-risk | 08 T31 | AI assistance can be detected and labelled, not prevented | Default off; `via` marking; AI seats labelled with their owner; rules page | M8 |
| F-8 | accepted-risk | 08 §6 | Shared, unprotected CI runners: MR and `main` jobs share hosts | Unprivileged jobs, rootless image builds; secrets only in variables that are both protected (protected `main` and `v*` tags) and environment-scoped (`release`, `renovate`, `production`) — our GitLab CE has no protected environments; protecting runners is an owner-side change; `publish:packages` runs dev tooling (Changesets, installed with `--ignore-scripts`) while the release deploy token is present (a fresh clone, `GIT_STRATEGY: clone`; `publish:image` has no checkout at all); "Use separate caches for protected branches" is on, so MR pipelines can't seed caches the release jobs read. Residual: all merge-request pipelines share the unprotected caches, so one MR's job could plant a tool or package there for later MR jobs. The mise binary is unpacked afresh from an archive whose SHA-256 is checked on every run, and pnpm checks store contents against their recorded hashes, but tools mise installed earlier are not re-hashed. Only maintainers push branches to this project, and merge requests from forks run in the fork's project, so the MR author is already trusted with the repository | M2 |
| F-9 | accepted-risk | 08 §6 | Images and packages are not signed yet | Publishing only from `main`/tags in the `release` environment, with credentials held in protected, environment-scoped variables; protected packages and container repositories (both exist on our CE). Packages use a deploy token (whether protected packages accept it is checked in M1; fallback: a Maintainer project access token). Images already use that fallback, because the protected container rule refused the deploy token (it has no role) on the first `main` pipeline: `RELEASE_REGISTRY_TOKEN` is a Maintainer-role project access token with only `read_registry` and `write_registry`. Its blast radius: it can push or overwrite any image in this project's container registry and nothing else; it can't call the API, push code or publish packages. Protected variables and refs are its only confinement; deploy by digest; possibly open: whether a Maintainer-triggered MR pipeline's `CI_JOB_TOKEN` can push a protected container tag or a `@your-move/*` package version (job-token git push is off) — checked in M1 (10 M1); if it can, protection is raised to Owner | Before third-party deploys |
| F-10 | accepted-risk | 08 §6, M0 review S-7 | Container images are built with a community fork of kaniko (osscontainertools, Apache-2.0), unsigned | Upstream kaniko is archived and rootless BuildKit needs user namespaces our unprivileged runners don't grant (ADR 0003); pulled from the fork's organisation registry (`ghcr.io/osscontainertools`) pinned by digest; its images carry unsigned build provenance only; every Renovate digest or version bump is reviewed against the fork's release notes (`review-release-notes` label) | M4 |
