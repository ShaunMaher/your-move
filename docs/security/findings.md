# Security findings and accepted risks

Tracks security findings and knowingly accepted risks (08 §7). Ids are `F-<n>`; status is
`open`, `fixed` or `accepted-risk`. Every OSV ignore in `osv-scanner.toml` names an entry here
with the same expiry (11 §6).

| Id | Status | Source | Risk | Rationale and mitigations | Review by |

| F-1 | accepted-risk | 06 §3 | Per-email OTP verify lockout (temporary denial of service) | Bounds guessing; temporary; logged | M2 |
| F-2 | accepted-risk | 08 T20 | Past-opponent relationships spread through N-player auto-joins | Both-acted rule; `whoCanAddMe = nobody`; games with AI seats always invite | M4 |
| F-3 | accepted-risk | 08 T4 | Q3 residuals: signing up, then accepting or declining, reveals that an address has an account | Needs the address holder's own action | M4 |

| F-5 | accepted-risk | 08 T27 | Installed game packages are fully trusted: a malicious one can compromise the instance and players' accounts | Install only trusted authors; review diffs; built-output rules and globals allow-list; test kit incl. isolation; Node code generation off and secrets scrubbed before loading games; CSP; no automerge; SES/isolates later; the engine lint rules are static: they reject built-ins used other than by name (an `instanceof` right-hand side, an error class as a class heritage, and `Number`/`String`/`Boolean` as an array method's callback count as by name), a built-in's members (its `prototype` and methods, however deep the chain) taken as values rather than called or reached through, writes, deletes and destructuring assignments to any member chain rooted at a built-in, `Object`/`Reflect` functions that change a built-in or its members (`assign`, `define*`, `setPrototypeOf`, `freeze`, `seal`, `preventExtensions`), reflective, descriptor and prototype access (`Object.getPrototypeOf`, `Reflect.getPrototypeOf`), dynamic `import()`, `import.meta`, and `constructor`/`__proto__`/`__lookupGetter__`/`__lookupSetter__`/`__defineGetter__`/`__defineSetter__` reached through a value by name, by a static key (string or template literal without expressions) or by destructuring. The residual: they can't follow a property name computed at run time, and they can't tell a user-defined function named like an array method (`map`, `filter`, …) from the built-in one, so an engine's own `map` that receives `Number`, `String` or `Boolean` as its "callback" could write to them through that parameter, and calls on a built-in's members are allowed, so a call that returns the built-in itself (such as `valueOf()`) yields an alias the rules don't follow; they are a guardrail, not a sandbox (built-output rules and the test kit, M1, narrow this; isolation later); scrubbing `process.env` guards against accidental leaks only — the original environment stays readable from `/proc/self/environ`, so secrets are best given as `*_FILE` (docs/deploy.md) | First third-party game |
| F-6 | accepted-risk | 08 T30 | Config controls who is admin; admins who also play on their admin account | Exclusive admin tokens of ≤ 30 days, audited, every admin notified on creation; docs say not to play on admin accounts | M3 |
| F-7 | accepted-risk | 08 T31 | AI assistance can be detected and labelled, not prevented | Default off; `via` marking; AI seats labelled with their owner; rules page | M8 |
| F-8 | accepted-risk | 08 §6 | Shared, unprotected CI runners: MR and `main` jobs share hosts | Unprivileged jobs, rootless image builds; secrets only in variables that are both protected (protected `main` and `v*` tags) and environment-scoped (`release`, `renovate`, `production`) — our GitLab CE has no protected environments; protecting runners is an owner-side change; `publish:packages` runs dev tooling (Changesets, installed with `--ignore-scripts`) while both release credentials are present: the deploy token and the Maintainer registry token (`RELEASE_REGISTRY_TOKEN`), since both publish jobs share the `release` environment scope until M1 gives each its own (10 M1) (a fresh clone, `GIT_STRATEGY: clone`; `publish:image` has no checkout at all); "Use separate caches for protected branches" is on, so MR pipelines can't seed caches the release jobs read. Residual: all merge-request pipelines share the unprotected caches, so one MR's job could plant a tool or package there for later MR jobs. The mise binary is unpacked afresh from an archive whose SHA-256 is checked on every run, and pnpm checks store contents against their recorded hashes, but tools mise installed earlier are not re-hashed. Only maintainers push branches to this project, and merge requests from forks run in the fork's project, so the MR author is already trusted with the repository. The first `@your-move/sdk`/`testkit` publish (0.1.0, M1a) happens before the M1 job-token and per-job environment checks. The residual is a compromised MR-pipeline dependency publishing a version through the job token. No third-party consumers exist yet. The M1 release-path work closes or records it. | M2 |
| F-9 | accepted-risk | 08 §6 | Images and packages are not signed yet | Publishing only from `main`/tags in the `release` environment, with credentials held in protected, environment-scoped variables; protected packages and protected container repositories (both configured on our CE). Packages use a deploy token (whether protected packages accept it is checked in M1; fallback: a Maintainer project access token). Images already use that fallback, because the protected container repository rule refused the deploy token (it has no role) on the first `main` pipeline: `RELEASE_REGISTRY_TOKEN` is a Maintainer-role project access token with only `read_registry` and `write_registry`. Its blast radius: it can push or overwrite any image in this project's container registry (including `v*` tags) and nothing else; deletion is reserved to Owner by the protection rule; it can't call the API, push code or publish packages. Our CE's npm package protection rule takes no delete level. Protected variables and refs are its only confinement; deploy by digest; possibly open: whether a Maintainer-triggered MR pipeline's `CI_JOB_TOKEN` can push to a protected container repository or a `@your-move/*` package version (job-token git push is off) — checked in M1 (10 M1); if it can, protection is raised to Owner and the registry token is reissued with the Owner role. The first `@your-move/sdk`/`testkit` publish (0.1.0, M1a) happens before the M1 job-token and per-job environment checks. The residual is a compromised MR-pipeline dependency publishing a version through the job token. No third-party consumers exist yet. The M1 release-path work closes or records it. | Before third-party deploys |

| F-11 | accepted-risk | 02 §6, M1b part 2 review S-1 | Test hooks ship in production engines: every `GameDefinition` carries its `test` hooks (part of the contract), so the words engine's bundle on the server and in browsers includes its kit bot and kit word list plus the test bot and worst-case code (about 18 KB unminified in all; the word list alone is about 5 KB, 2.7 KB gzipped) | Framework and runtime code never reads `test` (02 §6), enforced by `scripts/src/ci/test-hooks-unread.test.ts` over `packages/server/src`, `packages/shared/src` and `apps/*/src`; the hooks are pure engine code under the same built-output rules and kit as the rest of the engine; the kit word set is built only when the hook is called, never when the engine loads.
